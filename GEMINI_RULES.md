# Calendar Copilot - Development & Operations Rules

This document outlines the core principles, technology stack, and operational rules followed during the creation and maintenance of the Calendar Copilot application.

## 1. Core Principles
*   **Minimalist Aesthetic**: All UI elements must follow a "Notion-like" design system: clean typography (Inter), ample whitespace, and high-signal data density.
*   **Pastel Design System**: Interactive and categorical elements must use soft, pastel color palettes (e.g., `bg-blue-50`, `bg-purple-100`) rather than vibrant or saturated defaults.
*   **Robust Fallbacks**: The application MUST remain functional for demonstration purposes even if external API keys (Google, OpenAI, Gemini) are missing. This is achieved via sophisticated mock data generators.
*   **Privacy-First MVP**: The application initially requests `read-only` access to Google Calendar. No event data is stored permanently; only the essential OAuth tokens are kept in a local SQLite database.

## 2. Technology Stack
### Frontend (Vite + React + TypeScript)
*   **Styling**: Use Tailwind CSS (v4) for utility-first styling.
*   **Components**: Custom implementation of "Weekly Strip" and "Vertical Timeline" to allow granular control over event positioning.
*   **Transitions**: Use `framer-motion` for subtle micro-interactions only.
*   **Type Safety**: Strictly enforced TypeScript interfaces for all API response objects and application state.

### Backend (FastAPI + Python)
*   **Web Framework**: FastAPI for high performance and automatic Pydantic validation.
*   **Authentication**: `google-auth-oauthlib` for standard OAuth 2.0.
*   **Persistence**: SQLite (via SQLAlchemy) for local storage of user tokens.
*   **LLM Orchestration**: A custom router-tool-response pattern that allows switching between Gemini, OpenAI, or a deterministic Rule-Based Fallback.

## 3. Operational & Build Rules
### Running the Environment
*   **Consistency**: The Backend MUST run on port `8000` and the Frontend on port `5173`.
*   **CORS**: The Backend must explicitly allow requests from the Frontend URL via middleware.
*   **Single-Use Logic**: Google OAuth codes must be treated as single-use. Any failure during callback requires a restart of the flow from the Frontend.

### LLM Logic
*   **Router Step**: Every chat request must first be categorized by intent (e.g., `time_analysis`, `strategy`).
*   **Tool Step**: Statistics must be computed *before* reaching the LLM to prevent "hallucination" of calendar numbers.
*   **Fallback**: If `OPENAI_API_KEY` or `GEMINI_API_KEY` is not detected in `.env`, the `agent.py` must return a structured response generated by rule-based helpers in `tools.py`.

## 4. Development Workflow
1.  **Backend First**: Ensure the API models and database schemas are established before building UI components.
2.  **Environment Sync**: Use `.env.example` as the source of truth for required variables.
3.  **Atomic Edits**: Modify only one architectural layer at a time (e.g., fix the OAuth flow before adding new Chat features).
